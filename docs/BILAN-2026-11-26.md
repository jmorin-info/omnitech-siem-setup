# Bilan de livraison au 26 novembre 2026

Ce bilan distingue la distribution publiée, le code du dépôt et le dernier état
vérifié de la production. Un composant livré demande encore sa configuration et
sa recette sur chaque site.

## Livraison disponible

La [préversion signée 0.1.0-rc.5](https://github.com/jmorin-info/omnitech-siem-setup/releases/tag/v0.1.0-rc.5)
est publique. Elle contient les **1 052 fichiers suivis** de la révision
`3561371e8896074536a8785767e76e7afe7818ab`, dans un `.deb`, un `.rpm` et une
archive source avec les métadonnées Git nécessaires. Les dix pièces jointes
comprennent les signatures détachées, `release.json`, le manifeste SHA-256 et sa
signature. Le RPM porte également une signature interne.

Le [dépôt APT/DNF](https://jmorin-info.github.io/omnitech-siem-setup/) est hébergé
sur GitHub Pages, dans le canal **testing**. L’identité de signature est
**Julien Morin (OMNI SIEM releases)** ; empreinte primaire :
`2668CC327A9ADCB1AE585187AE984C65217DB120`.
Suivre [les commandes de confiance et d’installation](DISTRIBUTION-SIGNATURES.md),
puis [le parcours de déploiement](DISTRIBUTION.md).

Les paquets livrent le projet et `omni-siem`. Leur installation, réinstallation
ou suppression ne remplace pas le dépôt actif, ses paramètres ou ses bases et ne
redémarre pas le SIEM. Le socle et les modules s’installent par des commandes
explicites après configuration et lecture du plan.

Les candidates `rc.1`, `rc.3` et `rc.4` restent non publiées. Leurs tags et leurs
brouillons sont conservés, les brouillons remplacés étant identifiés comme tels.
La [préversion rc.2](https://github.com/jmorin-info/omnitech-siem-setup/releases/tag/v0.1.0-rc.2)
reste disponible avec ses garanties initiales : ses fichiers n’ont pas été
remplacés et ne sont pas rétroactivement signés.

Un contrôle client indépendant a également vérifié les signatures téléchargées
publiquement, le catalogue APT, le téléchargement du `.deb` et sa somme, puis
l’installation du RPM signé depuis le dépôt HTTPS dans un conteneur Rocky Linux 9.
Le paquet n’a pas créé de dépôt actif lors de cet essai.

Les tests couvrent aussi les fichiers de certificat public contenant plusieurs
clés ou des données privées : ils sont refusés. L’import de clé en CI refuse une
clé principale privée réelle. Seule la sous-clé chiffrée est utilisée dans
l’environnement GitHub réservé à `main`.

Ces contrôles ne prouvent pas la compatibilité de tous les firmwares, l’efficacité
de toutes les détections ou un serveur SIEM complet sur un OS RPM. Les cas
synthétiques ne remplacent pas la recette des équipements réellement installés.

## État de la production de référence

Le dernier déploiement vérifié dans cette conversation est celui de la carte
mondiale, le 26/11/2026 à 09:30 UTC :

- Dépôt actif à `28b88c629c4b8442b395a1dd37612becf0e6ff5b`, sans modification suivie ;
  console publiée et périodes vérifiées sur les données réelles.
- Configuration et pages locales conservées, dont la page de vulnérabilités
  développeur ; seul le backend SOC a été redémarré.
- Graylog, OpenSearch et MongoDB n’ont pas été redémarrés. Le contrôle de santé a
  réussi, avec un avertissement déjà connu sur les références à d’anciens chemins.
- Les huit services examinés lors du contrôle précédent utilisaient le dépôt
  canonique. Un seul administrateur SOC était alors configuré.

La préparation de la distribution signée n’a déployé aucun changement sur cette
production ni sur le contrôleur de domaine. L’alerting mail fait l’objet d’un
chantier parallèle : son état courant n’est pas certifié par ce bilan. Une mise
à jour ultérieure doit d’abord rapprocher ses modifications avec le dépôt.
La réception physique des nouvelles sources WatchGuard n’est pas démontrée par
les tests de VM.

## Limites et travaux encore ouverts

1. **Sources et agents** : terminer l’assistant complet de configuration,
   vérification de réception et liaison aux pages SOC. L’enrôlement Windows avec
   vérification de confiance initiale reste à durcir et à qualifier.
2. **Détails SOC** : les preuves détaillées d’alertes/corrélations, diagnostics
   WatchGuard et extensions de widgets des PR #12 et #14 restent en qualification,
   hors des paquets rc.5.
3. **Production** : rapprocher les changements parallèles avant tout déploiement,
   vérifier les tâches différées, traiter les anciennes références et définir un
   second administrateur humain pour les actions exigeant une double validation.
4. **Plateformes** : Ubuntu 26.04 reste expérimentale. Qualifier le socle sur les
   autres OS annoncés et les formats/firmwares réels de chaque site. Le serveur
   natif sur RPM reste refusé.
5. **Reprise** : réaliser l’exercice complet de sinistre et une copie de sauvegarde
   hors serveur. Une restauration MongoDB seule ne valide pas la reprise globale.
   Le juge LLM reste reporté selon la décision du site.
6. **Publication durable** : conserver une sauvegarde externe récupérable de la
   clé, préparer les migrations de confiance et compléter la conservation de
   plusieurs versions dans les catalogues. Les anciennes releases signées restent
   disponibles sur GitHub.

L’adoption conserve les données MongoDB/OpenSearch et les montages. Si les données
d’une base sont dans l’ancien dépôt, ce dossier reste nécessaire jusqu’à une
migration spécifique au moteur. Un chemin ambigu ou non reconnu provoque un refus
avant modification.

## Préparation de la 1.0 bêta : publication signée

La chaîne de signature et le canal testing sont opérationnels. L’identité,
les permissions, les commandes clientes, les erreurs, le renouvellement et la
gestion de la clé sont décrits dans [le guide de publication](DISTRIBUTION-SIGNATURES.md).
La première tentative a été arrêtée avant signature faute d’accès au brouillon ;
le correctif de permissions est intégré dans `main`, sans modifier les paquets
qualifiés du tag. Les attestations de provenance GitHub formelles restent une
amélioration distincte des signatures GPG et des références de preuves intégrées.

**La version 1.0 stable n’est pas publiée.** Les métadonnées signées de rc.5
conservent explicitement `stable_qualified: false`,
`server_rpm_qualified: false` et le statut expérimental d’Ubuntu 26.04.
La signature garantit l’identité des fichiers ; les limites ci-dessus restent
applicables à leur déploiement.
